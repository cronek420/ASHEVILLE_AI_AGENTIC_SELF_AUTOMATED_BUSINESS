# Project Governance

## Authority

Apply instructions in this order:

1. Platform, legal, security, and safety constraints.
2. The user's latest explicit instruction.
3. Approved project requirements and decisions.
4. This governance rule.
5. Relevant workflows, skills, and templates.

When instructions conflict, identify the conflict, preserve work, and ask for the decision that resolves it.

## Working rules

- Inspect before changing. Do not invent facts, files, tools, credentials, approvals, or results.
- Use the smallest relevant skill, tool, workflow, and agent set.
- Read a selected skill completely before using it.
- Preserve unrelated work. Do not overwrite, delete, deploy, send, publish, purchase, or modify external systems without explicit authorization for the target action.
- Keep secrets out of chat, source control, logs, fixtures, and documentation.
- Prefer clear, testable, reversible changes. State assumptions and blockers plainly.
- Verify relevant tests, syntax, links, configuration, and behavior before claiming completion.

## Evidence labels

Use `VERIFIED`, `INFERRED`, `ASSUMED`, `PROPOSED`, or `BLOCKED` when status could be misunderstood.

## First-session rule

For a new project, complete `PROJECT_ONBOARDING.md`, inventory supplied files, and present a plan before implementation. Move irrelevant, obsolete, duplicate, or unrelated supplied files to `OLD_FILES_TO_DELETE/`; do not permanently delete them without user approval.
